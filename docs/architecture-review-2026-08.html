B — The canonical loop burns two budget units per step

Strong · bug in-process

src/Runner/Execution/WorkflowExecutor.php:82–96 · src/Runner/Execution/WorkflowEngine.php:52–53

Problem. executeCanonically() calls transition() twice per step; each call runs spendStep(), so every step spends 2 of the maxSteps budget — and action criteria evaluate twice against mutated state.

Solution. One transition per completed attempt. Card A's run-state module removes the tangle that hid this; until then it's a two-line fix.

Before — one step, two transitions

step executes → success
transition() #1 → spendStep() (budget 1)
transition() #2 → spendStep() (budget 2)
next step…

maxSteps budget halves for every workflow; retry/goto criteria run twice

After — one transition per attempt

step executes → success
transition() → spendStep() (budget 1)
next step…

budget semantics match StepBudgetExceededException's contract

  • correctness: budget matches its declared meaning
  • locality: transition evaluation happens once, in one place

C — Give compilation a home again

Strong ports & adapters

src/Runner/Execution/StepExecutor.php · HttpStepExecutor.php:40–125 (×8 commits) · AsyncApiStepExecutor.php:99–168 (×8)
ArazzoOutputExtractor (×6) · ArazzoSchemaValidator (×6) · ExpressionResolverInterface (×4) · ArazzoExpressionResolver (@deprecated, still bound)
history: ArazzoRequestCompiler.php (257 lines) deleted in 5b88b0d, Aug 21

Problem. Three days ago 5b88b0d deleted the standalone Request Compiler and pushed its compile logic into HttpStepExecutor (+72 lines) and StepExecutor (+119 lines). Compilation now has three homes — StepExecutor, HttpStepExecutor, AsyncApiStepExecutor each re-implement "parameters + payload → request" — with visible drift between the sync and queued pipelines' request records, while Output Extractor and Schema Validator churn fused into the same call paths. The glossary still names a Request Compiler; the code says it must not exist as its own module, yet its behaviour keeps multiplying across executors.

Solution. Not the old module back — a home *behind the seams 5b88b0d created*: compilation lives inside the OpenApi executor / protocol-executor seam as shared implementation, consumed by all three call sites. One interface, three adapters' worth of callers, zero duplication.

Contradicts the decision in 5b88b0d — but worth reopening: that commit traded one shared compiler for triplicated compilation. The seam it created (OpenApiExecutorInterface, StepProtocolExecutorInterface) is the right place for compilation to live again — as internal implementation behind those seams, not as the parallel module that was dissolved.

F — The composition root is the #1 hot spot

Strong composition

packages/laravel/src/LaravelArazzoServiceProvider.php — 393 lines · 28 singleton bindings · touched by 19 of the last 300 commits (unchallenged #1 across ~86% of project history)

Problem. The most-churned file in the codebase contains no domain behaviour — it's pure composition. Because core modules have wide interfaces (Card D), every internal refactor leaks into this file: widening one constructor means re-editing a hand-ordered 28-binding graph here. It happened again this week — StepOutcomeHandler grew a parameter and the provider broke with 28 static-analysis errors. Concentration is right for a composition root; this much surface area is not.

Solution. Modules compose their own internals: each deep module exposes how to build itself from the ports it truly varies across, so the provider only binds framework-varying seams. Provider edits become rare because module-internal rewiring stops escaping.

E — Seam hygiene: keep the ports, delete the dead seams

Worth exploring ports & adapters

Runner/*/Contracts/*Interface.php · ArazzoExpressionEvaluator.php · ExecutionLoggerInterface.php

Problem. Six infrastructure interfaces have exactly one adapter each — hypothetical seams. They earn a documented exception (core must not know Illuminate; the Laravel adapter is the point), but two seams have zero or fake variation: ExecutionLoggerInterface has no adapter anywhere, and ArazzoExpressionEvaluator is a pass-through over ExpressionEvaluator invented for a single implementation.

Solution. Keep the six ports with a one-line rationale where they're defined; delete the logger interface (and its unused optional consumer), inline the pass-through evaluator.

Top recommendation

A — Unify the run-state module, taking B with it

The double-transition bug (B) was findable only because mapping knowledge has no locality — the same shallowness that hides it also spreads it. Build the run-state module first and B becomes a one-line consequence instead of a patch on a loop you don't fully see.
