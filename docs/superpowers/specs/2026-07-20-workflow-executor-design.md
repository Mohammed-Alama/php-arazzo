# Arazzo Workflow Executor Design

## Overview
This document outlines the design for the `WorkflowExecutor` in the `laravel-arazzo` package. The executor is designed as a **Framework-Agnostic Core**, enabling it to be used in any PHP application (Laravel, Symfony, Drupal) for running production business workflows based on the Arazzo 1.0.0 specification.

## Core Principles
1. **Framework Agnosticism**: The core execution logic will rely exclusively on standard PHP and PSR interfaces, with zero direct dependency on Laravel-specific helpers (e.g., `Illuminate\Support\Collection` or `Http` facade).
2. **Decoupling from Parser**: The execution engine will only consume immutable DTOs generated by the existing Arazzo Parser.
3. **Pluggability**: Consumers can swap out the HTTP client, logger, and state storage mechanism.

## Architecture & Components

### 1. The Execution Namespace
All execution logic will reside in `Alama\LaravelArazzo\Execution\`.

### 2. PSR Contracts
To ensure framework agnosticism, the executor will depend on the following PSRs:
- **PSR-18 HTTP Client** (`psr/http-client`): For executing API requests.
- **PSR-17 HTTP Factories** (`psr/http-factory`): For constructing PSR-7 Request objects.
- **PSR-3 Logger** (`psr/log`): For logging execution progress and errors.

### 3. Core Classes

#### `WorkflowExecutor`
The main entry point for executing a workflow.
- **Responsibilities**:
  - Accepts a `Workflow` DTO, initial inputs, and credentials.
  - Builds the dependency graph (via `DependencyGraph`).
  - Initializes the `VariableContext`.
  - Loops through the steps in topological order and delegates to `StepExecutor`.
  - Returns a final `ExecutionResult` DTO.

#### `StepExecutor`
Executes an individual workflow step.
- **Responsibilities**:
  - Resolves parameters from the `VariableContext` via the existing `Resolution` module.
  - Translates Arazzo request definitions into a PSR-7 `RequestInterface`.
  - Dispatches the request via the PSR-18 `ClientInterface`.
  - Evaluates `successCriteria` using the response.
  - Extracts outputs using JSONPath (e.g., `flow/jsonpath` or similar library).

#### `VariableContext`
Maintains the state of the workflow during execution.
- **Responsibilities**:
  - Stores `$inputs`, `$steps` outputs, and environment variables.
  - Exposes methods for the existing `Expression` system to query state.

#### `DependencyGraph`
- **Responsibilities**:
  - Analyzes the `dependsOn` field of all steps.
  - Performs a topological sort to determine execution order.
  - Detects and throws exceptions on circular dependencies.

## Data Flow

1. **Initialization**: `WorkflowExecutor::execute($workflow, $inputs)` is called.
2. **Planning**: `DependencyGraph` determines the order: e.g., `[StepA, StepB, StepC]`.
3. **Execution Loop**:
   - For `StepA`: `StepExecutor` resolves parameters -> Builds PSR-7 Request -> Sends via PSR-18 Client -> Evaluates success -> Extracts outputs.
   - Outputs are pushed into `VariableContext`.
4. **Finalization**: `WorkflowExecutor` extracts final workflow outputs and returns an `ExecutionResult`.

## Laravel Integration
While the core is framework-agnostic, the package will provide a seamless Laravel experience via the `LaravelArazzoServiceProvider`. 
- It will automatically bind Laravel's HTTP Client (or a Guzzle instance) to the PSR-18 interface and Laravel's Log manager to the PSR-3 interface.
- Laravel users will not need to manually configure the PSR implementations.

## Error Handling & Resilience
- Step failures (HTTP errors or failed success criteria) will throw specific exceptions (e.g., `StepExecutionFailedException`).
- Future enhancements will implement the `onFailure` retry and fallback behaviors specified in the Arazzo standard.
